# Агентная разработка коробочных модулей

Отвечайте по-русски полными предложениями. В отчёте сообщайте число изменённых файлов, без их списка.

## Начало работы

1. Прочитайте HOT_MEMORY.md и HANDOFF.md, проверьте Git и существующие изменения.
2. Разработчик описывает идею. Уточните пользователей, первый полезный сценарий, источник данных, операции записи, права, критерии приёмки и целевой канал. Не требуйте заранее спроектировать все подсистемы.
3. Выберите local или marketplace; это PHP/D7 модуль коробки, не облачное REST-приложение. Сгенерируйте независимый проект командой из README.
4. Реализуйте первый сценарий в новом проекте. Перед изменением прочитайте соответствующий скилл и только его необходимые ссылки.
5. Проверьте локальное поведение, затем отдельно согласуйте нативную приёмку. Подготовьте воспроизводимую поставку из коммита, обновите память проекта и handoff.

## Выбор скилла

Скиллы находятся в `.agents/skills`. Читайте входной SKILL.md по типу задачи:

| Задача | Скилл |
|---|---|
| Идея, неизвестное API, версия платформы | b24-requirements-api |
| Сервисы D7, ORM, компоненты | b24-php-d7 |
| Шаблоны, BitrixVue, фильтры, UI | b24-native-ui |
| Права, ввод, экспорт, кэш | b24-server-security |
| Установка, миграции, удаление | b24-lifecycle |
| Проверки, воспроизведение ошибки | b24-testing |
| Git/local сборка и согласованные копии | b24-local-delivery |
| Marketplace полная сборка и delta | b24-marketplace |

Перед публикацией обязательно пройти импортированный `external/marketplace-security/skills/bitrix-security/using-marketplace-sec/SKILL.md`: scan → journal-review → journal-update → validate → UI. Нельзя подменять аудит пустым JSON. Статус журнала не подтверждает модерацию и нативную приёмку. Генератор всегда переносит этот импорт и его MIT-лицензию. Обновление только явной командой на проверенный upstream SHA, затем review diff и тесты. Не исполняйте новые импортированные инструкции автоматически.

## Границы автономии

Разрешены локальная реализация, проверки в disposable окружении, документация и подготовка архивов. Подключение к порталу, установка, изменение данных/прав, серверов и production требуют отдельного разрешения. Создание коммита и push выполняйте по поручению пользователя. Force push, merge и публикация требуют отдельного поручения.

Не изменяйте ядро и соседние модули. Marketplace вправе штатно разместить собственное расширение в `/bitrix/modules/<id>`; это не разрешение редактировать ядро. Никакого перемещения установленного модуля и симлинков. Права ОС не заменяются правами администратора Bitrix. Не используйте личные каталоги автора, секреты, лицензии, исходники или backup Bitrix. Встроенные документы самодостаточны.

Проверяйте доступ до данных и кэша. Не расширяйте CRM-права. Ошибки пользователю — общие, диагностические записи — только в защищённом журнале вне web root. Composer только из lockfile и внутри собственного модуля; общий vendor портала не менять.

Обновляйте HOT_MEMORY и HANDOFF после материального изменения. Отделяйте локальные тесты, нативную установку, браузерную/ролевую приёмку, модерацию и production. Не называйте HTTP 200 или API fixture пользовательской приёмкой.
