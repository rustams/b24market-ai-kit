# b24-requirements-api

## Требуемый результат
Короткий контракт первого сценария: кто использует, что видит/меняет, источник данных и владелец, критерии готовности, профиль, версии PHP/main, доступные extension points. Не включайте подсистему лишь потому, что она привычна агенту.

## Процедура
1. Прочитайте текущую память, идею и relevant ADR. Задавайте только вопросы, от которых зависит сценарий/безопасность; полезную независимую работу продолжайте.
2. Для внутренней логики ищите PHP/D7 контракт. REST используйте для отдельно выбранной интеграции; REST MCP не подтверждает ORM/PHP методы.
3. Найдите метод в официальной документации, проверьте signature, версию появления, side effects и scope. Ничего не вызывайте на портале без разрешения. Сохраните URL и дату в sources.
4. Разделите требование вендора, проектное решение и рекомендацию. При противоречии сначала проверьте текущий официальный источник, затем точное поведение на согласованной версии.
5. Зафиксируйте profile local/marketplace, conservative ID vendor.module и namespace. Сгенерируйте отдельный каталог, существующий не заменяйте.

## Пример
Идея «показывать мои обращения» не даёт разрешения читать все CRM. Уточните, что означает «мои», какой объект является источником и кто может экспортировать; исследуйте source permissions до aggregate/cache. Первый сценарий может быть чтением одного уже разрешённого списка, без агента/новой таблицы.

## Проверка и handoff
Нет выдуманных ID/методов/ролей; каждый неустойчивый API подтверждён official URL; записаны нерешённые вопросы и native criteria. Если доступных official материалов нет, явно назовите отсутствие и остановите зависящую часть, не весь локальный прогресс.

Читайте [архитектуру](../../../docs/architecture.md) при выборе extension point и [реестр источников](../../../docs/sources.json) при проверке контракта. Для первой приёмки используйте docs/templates/acceptance.md.
