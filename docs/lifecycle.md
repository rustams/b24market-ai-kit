# Жизненный цикл

Проектное решение: проверка admin + POST + CSRF перед установкой и удалением. Новая установка проверяет PHP/main, движок при включённом storage, симлинки, конфликт файлов и запись. Только после этого копирует собственный компонент и регистрирует модуль, применяет миграции и сохраняет manifest. Новые таблицы создаются лишь по выбору storage.

Если копирование/регистрация/миграция ломается, установка восстанавливает прежние собственные файлы и опции, снимает новую регистрацию, удаляет только вновь созданную таблицу. Ошибки rollback тоже журналируются, успех не объявляется. Компенсация защищает исключения в процессе, но не остановку питания/процесса. До нативных операций администратор делает backup кода/БД вне document root. У MySQL DDL нет обещания транзакционного отката.

Повторный DoInstall зарегистрированного модуля ничего не переустанавливает. Для обновления используйте отдельный updater/CLI. Сохранённое приветствие и строки таблицы сохраняются. Миграции — нумерованные idempotent closures; добавляйте в возрастающем порядке. Выпущенную миграцию не переписывать. Marker schema_version обновляется после успешной миграции. Reconciliation первой миграции восстанавливает отсутствующую таблицу и обнуляет storage_cursor, оставляя несвязанные настройки.

Marketplace апдейтер не использует новые классы модуля: функции возвращаются из support-файлов в payload обновления. Он выполняется до штатного копирования кода; ошибка ставит errorMessage, откатывает компонент. Глобальная атомарность всей последующей операции SiteUpdate не обещается. Если этап кодового копирования упал после миграции, восстановление выполняется из согласованного backup.

Local deployment содержит и модуль, и активный компонент из одного commit. После доставки запустите update-local для reconciliation файлового manifest и миграций. Не запускать DoInstall. При сохранённых неизвестных/кастомных файлах остановитесь и согласуйте их судьбу. Автоматическое удаление старых файлов блокируется до отдельной документированной миграции.

## Судьба объектов

| Объект | Удаление по умолчанию | Явный purge |
|---|---|---|
| Таблицы и строки | Сохраняются | Удаляется только собственная таблица |
| Настройки, manifest, cursor | Сохраняются | Option::delete только собственного ID |
| Активный компонент | Удаляются только перечисленные файлы с совпавшим hash | Так же |
| Неизвестные/изменённые файлы | Сохраняются, конфликт останавливает операцию | Сохраняются |
| Публичные страницы/меню | Не создаются и не меняются | Не меняются |
| Исходный каталог модуля | Управляется штатным клиентом, не перемещается | Так же |
| Кэш | Собственный каталог очищается | Так же |
| События и агенты | В базовом проекте отсутствуют | Отсутствуют |

При добавлении handlers/agents выключайте их при обоих видах удаления, без удаления чужих callback. После сохранения и переустановки зарегистрируйте ровно один экземпляр. Отдельно тестируйте оставшиеся опции при удалённых таблицах. Полное удаление необратимо для пользовательских данных; ошибка purge требует восстановления backup, не blind retry.

Проверка manifest — защита от случайной потери кастомизаций, не защита от администратора с записью в code/DB. Устанавливать и обновлять нужно в согласованном окне с запретом конкурентных deployments; request-wide и cluster-wide atomicity не реализованы.
